Reference

Guía de uso

Cómo crear un componente, una variante o una versión nueva, cambiar su estado, ordenar las variantes, renombrar, ocultar y eliminar, con la IA (Claude Code) y las skills del proyecto. Las skills generan solo la estructura: los estilos, el marcado y la lógica los escribe el maquetador. Las excepciones son Replicar de PrimeNG, que implementa el componente completo, y Estandarizar un componente, que alinea lo que un maquetador hizo fuera del repo.

@for (section of sections; track section.id) { {{ section.name }} }

Cómo pedírselo a la IA

Una skill es un conjunto de instrucciones guardado en .claude/skills/<nombre>/SKILL.md . Claude Code la carga cuando la tarea coincide y sigue sus pasos: qué preguntar, qué script ejecutar y qué no tocar. Así todos los componentes salen con la misma estructura.

1. Con el comando

Escribe / y el nombre de la skill en el chat de Claude Code. Puedes pasar datos a continuación. 

/crear-variante accordion Icons + Border

2. En lenguaje natural

Pídelo como se lo pedirías a un compañero; la IA reconoce la skill que corresponde.

Crea una nueva versión del componente button

Buenas prácticas

  • Da todo en un solo mensaje (componente, título, descripción). Lo que falte, la IA lo pregunta junto, también en un solo mensaje.
  • Usa el nombre visible de la referencia (Excel / Figma): Icons + Border , Dropdown / Select . El id y slug se calculan solos ( icons-border ).
  • La descripción es una línea y puede quedar vacía; se cambia luego en la cabecera del HTML.
  • No pidas CSS ni marcado al crear: la base se entrega solo como plantilla y la variante aparece como Preview pending hasta que escribas el ejemplo.
  • Revisa el resultado con npm start (http://localhost:4321); las carpetas nuevas aparecen solas en el menú.

Crear un componente

Skill: /crear-componente

Crea un componente int-* nuevo con toda su estructura de documentación, listo para maquetar. Úsala cuando el componente todavía no existe en el menú.

Qué te pregunta

  1. Título del componente ( Chip ). El id se deriva en kebab-case ( chip ).
  2. Descripción del componente (una línea, opcional).
  3. Descripción de la variante Basic (opcional).
  4. Diseñador a cargo (Yony León, Gabriela Javier o Christian Abanto).

Al final pregunta "¿Deseas crear otra variante?" y, si dices que sí, sigue con /crear-variante .

Cómo pedirlo

/crear-componente
Crea el componente Chip. Descripción: "Chips represent entities using icons, labels and images."
Crea el componente Tag y después las variantes Severity y Rounded

Qué genera

src/components/chip/
├── version-1/
│   ├── base/
│   │   ├── chip.html           aquí actualizas el título y la descripción del componente
│   │   └── chip.ts             <int-chip> con solo (status = 'pending') y (designer = 'tu nombre')
│   ├── styles/
│   │   ├── _chip.scss          plantilla de secciones (TOKENS · BLOCK…), sin CSS
│   │   └── _index.scss         punto de entrada (@use)
│   └── variants/
│       └── basic/              siempre se crea (Preview pending)
│           ├── example.html    aquí actualizas la cabecera de la variante; debajo va el código del ejemplo
│           └── example.ts      importa solo la base
├── chip-page.ts                página de documentación (<app-doc-page>)
├── chip.config.ts              id del componente (+ orden u ocultar variantes)
└── routes.ts                   ruta /components/chip

Solo se trabaja dentro de version-N/ . chip-page.ts , chip.config.ts y routes.ts (atenuados) los crea la skill y no se tocan. También lo registra una vez en src/components/inventory.ts (posición en el menú). Es el único registro manual: variantes y versiones se detectan solas.

Crear una variante

Skill: /crear-variante

Agrega un ejemplo (una sección de la documentación) a un componente que ya existe. Cada variante es una carpeta variants/<slug>/ : aparece en el menú y en la página sin registrarla en ningún lado.

Qué te pregunta

  1. Componente : id o nombre visible ( accordion , Dropdown / Select ).
  2. Título de la variante ( Icons + Border , Raised ).
  3. Descripción (una línea, opcional).

Se crea en la versión más reciente, salvo que pidas otra.

Cómo pedirlo

/crear-variante accordion Icons + Border
Agrega la variante Raised a button: "Raised buttons display a shadow to indicate elevation."
Nuevo ejemplo Disabled de input en la versión 1

Qué genera

src/components/accordion/version-N/variants/icons-border/
├── example.html    solo la cabecera (title + description); debajo escribes el ejemplo
└── example.ts      AccordionIconsBorderExample: importa solo la base

Enlace directo: /components/accordion#accordion-icons-border . El título y la descripción se editan en la cabecera de example.html , nunca en un .ts .

Crear una versión

Skill: /crear-version

Abre version-N+1/ como copia exacta de la última versión (base, variantes y estilos) para cambiar la implementación sin romper la publicada. La versión anterior no se toca y la página muestra un desplegable de versiones.

Qué te pregunta

  1. Componente : te indica cuál es la última versión y cuál va a crear.
  2. Título en la versión nueva (por defecto, el mismo).
  3. Descripción en la versión nueva (conviene contar qué cambia).

Al final pregunta si quieres crear otra variante en la versión nueva.

Cómo pedirlo

/crear-version button
Crea la versión 2 de tabs con la descripción "Header with icon and badge."
Versiona demo, mismo título y descripción

Qué genera

src/components/button/
├── version-1/      intacta, sigue publicada
└── version-2/      copia de version-1: base/, variants/ y styles/
                    base/button.ts → comentario "version 2" y status = 'pending'
                    base/button.html → cabecera actualizada

Cada versión es enlazable con /components/button?version=1 ; por defecto se abre la más reciente. No confundir con una variante visual ( V1 / V2 de Tabs en el Excel), que es un modificador .int-tabs--v2 dentro de la misma versión.

Ocultar y reactivar

Skills: /ocultar /reactivar

Quita temporalmente un componente, una variante o una versión del sitio sin borrar código: solo cambia <id>.config.ts . Para volver a mostrarlo, /reactivar ; la variante vuelve a su misma posición.

Qué En el config Efecto
Componente hidden: true Fuera del menú, la búsqueda, la galería y Status; su URL deja de abrir.
Variante variants: [{ name: 'raised', hidden: true }] Fuera del menú y de la página, en todas las versiones.
Versión hiddenVersions: [1] Fuera del desplegable; ?version=1 abre la última visible. La última versión visible no se puede ocultar.

Cómo pedirlo

Oculta la versión 1 de tabs
/ocultar variante accordion raised
¿Qué tengo oculto?
Reactiva el tooltip

¿Qué tengo oculto?

Pregúntaselo a la IA: te muestra en el chat una tabla con todo lo oculto (componentes, variantes y versiones) y te pregunta qué volver a mostrar. Tú solo eliges; ella hace el cambio.

/reactivar

Ordenar variantes

Skill: /ordenar-variantes

Cambia el orden de las variantes en el menú y en la página. Por defecto va basic primero y el resto en orden alfabético. El orden es uno solo por componente: el menú junta las variantes de todas las versiones.

Cómo funciona

  1. Te muestra en el chat una tabla con la posición, el slug, el título y las versiones de cada variante.
  2. Le dices el orden completo o solo un movimiento ( raised en la 2 ).
  3. Guarda los slugs en variants de <id>.config.ts .

/crear-variante también te pregunta la posición cuando el componente tiene 3 o más variantes.

Cómo pedirlo

/ordenar-variantes accordion
Pon Raised en la posición 2 de button
Mueve Outlined al final en demo

Qué cambia

src/components/button/button.config.ts

export default {
  id: 'button',
  variants: ['basic', 'raised', 'outlined'],
  …
}

Se guardan slugs (nombres de carpeta), así que cambiar un título en example.html no rompe el orden. Una variante nueva que no esté en la lista va al final.

Renombrar

Skills: /renombrar-componente /renombrar-variante

Cambian el nombre técnico y con él la URL. Las versiones no se renombran. Si solo quieres cambiar el texto que se ve, basta con editar el title: de la cabecera del HTML.

Skill URL Qué renombra
/renombrar-componente /components/slider → /components/slidering Carpeta, archivos, <int-slider> , .int-slider* , IntSlider , inventory.ts y catalog-groups.ts . Opcionalmente, el título.
/renombrar-variante #slider-raiser → #slider-raised La carpeta variants/<slug>/ en todas las versiones, su selector y su clase, el título y su entrada en el config (conserva la posición).

Cómo pedirlo

/renombrar-componente slider slidering
Renombra la variante Raiser de accordion a Raised

Antes de confirmar

Te muestra todo lo que va a cambiar. El enlace viejo deja de funcionar y, en un componente, también cambian el selector y las clases: los proyectos que ya lo usen tendrán que actualizarse. Si otros componentes lo requieren o lo usan, también actualiza sus requires/uses y sus marcadores dep:.

Eliminar

Skills: /eliminar-variante /eliminar-version /eliminar-componente

Borran la carpeta y limpian lo que apunta a ella (config, inventario, src/generated/ ), así npm start no falla con un import que ya no existe. Primero te muestran qué se va a borrar, avisan si hay archivos sin commitear (git no podrá recuperarlos) y piden confirmación.

Skill Qué borra Qué más limpia No deja
/eliminar-variante version-N/variants/<slug>/ (si está en varias versiones, pregunta de cuál o de todas) Su entrada en variants del config Borrar basic sin confirmarlo explícitamente
/eliminar-version version-N/ completa; las demás no se renumeran Las variantes que solo vivían en esa versión Borrar la única versión
/eliminar-componente src/components/<id>/ inventory.ts y catalog-groups.ts Borrar Demo (referencia)

Cómo pedirlo

/eliminar-variante accordion raised
Borra la versión 1 de tabs
Ya no vamos a hacer el tooltip, elimínalo

¿Borrar del todo u ocultar?

Las tres skills te preguntan primero. Si eliges ocultar, el código se conserva y solo desaparece del menú, la búsqueda y la galería: se deshace con /reactivar (ver Ocultar y reactivar ). Borrar del todo solo se recupera con git, si estaba commiteado. Si otro componente lo requiere o lo usa, /eliminar-componente te avisa y recomienda ocultarlo.

Replicar de PrimeNG

Skill: /replicar-primeng

Copia un componente de PrimeNG v20 (estructura, estilos, API, teclado y ARIA) como un int-* propio que no importa nada de PrimeNG. Es la skill que sí escribe estilos, marcado y lógica: lee el código real en node_modules , toma los estilos y variantes de los casos .pr* de la base de conocimientos (Intelica.knowledgeBase), los traduce a tokens --i-* del Style Guide y agrega animaciones (ripple, fade de overlays) y navegación por teclado.

¿Por dónde empiezo?

Un componente entra al repo por uno de dos caminos, nunca por los dos. Desde ahí queda estándar y lo mantienen las skills de Mantenimiento, que no funcionan sobre un componente sin estandarizar.

1. Implementación

Punto de partida: uno u otro.

  • Se replica de PrimeNG desde cero, en un componente nuevo y limpio.
    ➜ /replicar-primeng
  • El componente se elaboró fuera de este repo.
    ➜ /estandarizar-componente

Resultado: un componente estándar.

2. Mantenimiento

Requiere un componente estándar.

  • Cambió el diseño.
    ➜ /sincronizar-componente
  • Se terminó un componente que usa.
    ➜ /resolver-dependencias

Orden de prioridad de las fuentes

# Fuente Qué define
1 PrimeNG v20 ( node_modules/primeng ) API, estructura, comportamiento, teclado, ARIA y animaciones. Se lee, nunca se importa.
2 Base de conocimientos ( Intelica.knowledgeBase ) Solo los casos .pr* : estilos, variantes y casos de uso. Se ignoran .pt* , .ly* y .gr* .
3 Style Guide ( Intelica.Style.Guide.New ) CSS de las clases .pr* , tokens --i-* y helpers .u-* para los templates de las variantes.
4 Figma Solo guía visual: no crea variantes ni cambia valores. Lo que solo está en Figma se reporta.

Qué te pregunta

  1. Siempre, en qué componente replicar (sugiere uno, p. ej. p-chip → Pill). Si no existe, te pide crearlo antes con /crear-componente .
  2. Si el componente ya tiene algo customizado : completar solo lo que está en plantilla, forzar (sobrescribir) o cancelar.

Sin forzar, nunca altera lo que ya escribiste. Cabecera, estado y diseñador se conservan siempre.

Cómo pedirlo

/replicar-primeng p-chip
Replica p-select de PrimeNG v20
/replicar-primeng p-chip https://www.figma.com/design/…?node-id=12-345

Con link de Figma: se usa como guía visual y para anotar la huella en cada token; los valores salen de la base de conocimientos (Intelica.knowledgeBase) y del Style Guide.

Qué genera

src/components/chip/version-1/
├── base/chip.ts      inputs/outputs con los nombres de PrimeNG, signals, OnPush
├── base/chip.html    misma estructura que p-chip con clases BEM .int-chip__*
├── styles/           _index.scss + _chip.scss (tokens --int-chip-* → --i-*)
└── variants/         basic, icon, image, removable, template, disabled

Al final informa qué se implementó, qué quedó fuera (PassThrough, unstyled …), las diferencias con PrimeNG, lo que solo está en Figma y el resultado de npm run check:component , npm run build y npm test . El estado queda en Pending hasta que lo cambies.

De dónde salen los tokens

Los tokens (color, spacing, sizing, radios, tipografía, opacidad, motion, etc.) se consumen siempre del repo Style Guide ( Intelica.Style.Guide.New ), preferiblemente sus Primitives / Alias con escala (xs, sm, md…). El componente solo declara alias --int-chip-*: var(--i-*) y sus reglas leen esos alias. Si un valor de PrimeNG no tiene token equivalente, la skill usa el más cercano y lo informa, o te pregunta; nunca escribe un valor fijo.

Estandarizar un componente

Skill: /estandarizar-componente

Para el componente que un maquetador replicó o customizó en su local, con su propia IA , y pegó sobre src/components/<id>/version-N/ . Lo deja como si lo hubiera hecho /replicar-primeng : estructura, clase Int<Id> , API con los nombres de PrimeNG, BEM int-* , tokens con comentario de origen, animaciones, teclado y marcadores de dependencias. Sin esas huellas, /sincronizar-componente y /resolver-dependencias no pueden trabajar sobre el componente.

Qué te pregunta

  1. Componente y versión; el link de Figma es opcional.
  2. Si lo pegado no está commiteado, te pide un commit [Import] - <id> raw from <maquetador> antes de tocar nada: así queda el original para comparar.
  3. Solo lo que ninguna fuente resuelve: una variante del maquetador que no está ni en la base de conocimientos (Intelica.knowledgeBase) ni en PrimeNG (conservar, ocultar o eliminar), un valor sin token o una dependencia dudosa.

Lo demás lo alinea con el orden de prioridad y lo reporta. Cabecera, estado y diseñador se conservan siempre. Si el trabajo envuelve PrimeNG ( <p-chip class="prChip"> , imports de primeng ), no se puede estandarizar: te avisa y lo rehace con /replicar-primeng usando lo del maquetador como referencia.

Cómo pedirlo

/estandarizar-componente chip
Estandariza el select que subió Yony
El maquetador pegó su tooltip, déjalo como replicar-primeng

Cómo funciona

  1. Diagnóstico (sin escribir nada): corre npm run check:component , lee el código pegado, PrimeNG y el caso .pr de la base de conocimientos (Intelica.knowledgeBase).

  2. Te muestra el mapa de API (nombre del maquetador → nombre de PrimeNG) y la tabla de adaptación:

    Conserva   lo que ya cumple
Renombra   archivo, clase, selector, BEM o input con otro nombre que PrimeNG
Alinea     difiere de PrimeNG o de la base de conocimientos (Intelica.knowledgeBase): gana la fuente y se anota
Agrega     animaciones, ripple, teclado, marcadores dep:, comentarios de origen
Quita      imports de PrimeNG, clases .pr*, valores fijos, mocks en la base

  3. Adapta : mueve los archivos con git mv , convierte cada valor en un token y deja los provisionales marcados: 

    // antes (maquetador)
.chip { gap: 4px; background: #eef2f6; }

// después
--int-chip-gap: var(--i-spacing-gap-xs); // knowledgeBase: --i-spacing-gap-xs · Figma: 4px (spacing/gap/xs) · Aura: 0.5rem
.int-chip { gap: var(--int-chip-gap); }

  4. Valida con npm run check:component (0 errores), npm run build y npm test , e informa los Cambios sobre el trabajo de <maquetador> con el porqué de cada uno, para devolvérselos.

Qué revisa

No tienes que ejecutar nada: la skill corre check:component por su cuenta al empezar y al terminar. El script revisa que un componente cumpla las bases: estructura, clase y selector, imports prohibidos, clases p-* / .pr* / PrimeFlex, tokens que existan en el Style Guide, helpers .u-* , duraciones fijas, :focus-visible y marcadores dep: . Los errores ❌ los corrige la skill; los avisos ⚠️ te los reporta.

Si trabajas con otra IA (Copilot, Cursor…), dale AGENTS.md de la raíz del repo: resume las reglas y así lo que subas llega casi alineado. Si quieres revisarlo por tu cuenta, el comando es npm run check:component -- <id> (o --all ).

Sincronizar un componente

Skill: /sincronizar-componente

Cuando el diseño en Figma de un componente ya implementado cambia. Lee el link guardado en la cabecera de base/<id>.html ( figma: ), compara el diseño con los comentarios // Figma: de los tokens y te muestra qué cambió. También revisa si cambió el caso .pr en la base de conocimientos (Intelica.knowledgeBase). Solo aplica lo que apruebes, siempre con tokens --i-* del Style Guide.

Figma no es la fuente de verdad: si cambia un valor que viene de la base de conocimientos (Intelica.knowledgeBase, // knowledgeBase: ) o del Style Guide ( // SG: ), el token no se toca; se reporta la diferencia para que el equipo actualice la base de conocimientos (Intelica.knowledgeBase). Tampoco crea variantes a partir de Figma.

Requiere un componente estándar, hecho con /replicar-primeng o /estandarizar-componente . Si lo hizo un maquetador fuera del repo, primero Estandarizar un componente .

Qué te pregunta

  1. Componente y versión; el link de Figma solo si no está guardado (sin link, sincroniza solo con la base de conocimientos).
  2. Tras el informe: aplicar , decidir variantes o estados nuevos y, si tocaste algo a mano, forzar o dejarlo.

No cambia la API ni el comportamiento. Para un rediseño grande propone una versión nueva.

Cómo pedirlo

/sincronizar-componente chip
/sincronizar-componente chip --solo-verificar
El figma de button cambió, actualízalo

Cómo detecta los cambios

Cada token lleva un comentario con su origen y con lo que se vio en Figma la última vez:

--int-chip-gap: var(--i-spacing-gap-sm); // knowledgeBase: … · Figma: … · Aura: …
Parte Ejemplo Qué indica
knowledgeBase: --i-spacing-gap-sm Origen del valor: la base de conocimientos (Intelica.knowledgeBase). Con SG: , el Style Guide.
Figma: 8px (spacing/gap/sm) Huella: lo que se vio en Figma la última vez. Sirve para detectar si cambió.
Aura: 0.5rem Valor original de PrimeNG, como referencia.

Qué te muestra

El informe sale en la terminal agrupado por estado, con una línea por token:

Sincronizar chip · version-1
Figma: …?node-id=12-345 · Base de conocimientos (Intelica.knowledgeBase): chip.md (MCP)

📘 Cambió en la base de conocimientos (se aplica)
   • gap: --i-spacing-gap-sm → --i-spacing-gap-md · _chip.scss
🔄 Cambió en Figma
   • padding-x: 12px → 14px · origen knowledgeBase: solo se reporta
✏️ Editado a mano (no se toca sin forzar)
   • radius: no apunta a su origen · _chip.scss
🆕 Solo en Figma (no se implementa)
   • estado Pressed
✅ Igual: 12 tokens
Otros estados posibles:
  • 🗑️ Ya no está en Figma: lo conserva si tiene origen; si no, te pregunta.
  • ❓ Sin huella: el token no tiene comentario Figma: ; compara con la base de conocimientos y solo reporta lo de Figma.

El link de Figma se ve en la página del componente como un chip Figma junto al estado. Con --solo-verificar solo informa, sin cambiar nada.

Resolver dependencias

Skill: /resolver-dependencias

Algunos componentes usan otros por dentro (un MultiSelect usa un Checkbox ). Cada maquetador replica el suyo sin esperar al otro: si el componente que necesitas aún no está en Done , /replicar-primeng pone en su lugar un provisional (un elemento nativo marcado) y lo anota en requires del config. Cuando ese componente se termina, esta skill cambia el provisional por el componente real.

Si el otro componente solo aparece en el contenido de una variante (el botón del pie de una Card ), es una dependencia opcional : va en uses y el provisional queda en el example.html . Ambas se ven en el chip Dependencies de la página del componente, con su estado y un enlace a cada una.

Requiere componentes estándar, hechos con /replicar-primeng o /estandarizar-componente . Si alguno lo hizo un maquetador fuera del repo, primero Estandarizar un componente .

Qué te pregunta

  1. Qué componente se terminó (p. ej. checkbox). Si no lo dices, te lista los provisionales pendientes.
  2. Solo si el componente real no cubre algo que hacía el provisional (un evento, un estado): qué hacer con ese punto.

Si la dependencia aún no está en Done, no toca nada. Nunca modifica el componente requerido ni lo customizado fuera de los marcadores.

Cómo pedirlo

/resolver-dependencias checkbox
El checkbox ya está listo, actualiza el multiselect
/resolver-dependencias --listar

Con --listar (o "¿en qué orden maquetamos?") muestra qué requiere cada componente y el orden de trabajo: primero los que no dependen de nadie.

Cómo funciona

  1. /replicar-primeng anota la dependencia en el config del componente: 

    // multi-select.config.ts
requires: ['checkbox'],

  2. Como el checkbox aún no está en Done , deja un provisional marcado en base/multi-select.html : 

    <!-- dep:checkbox provisional -->
<input type="checkbox" class="int-multi-select__checkbox" />
<!-- /dep:checkbox -->

  3. Cuando el checkbox pasa a Done , ejecutas /resolver-dependencias checkbox y el provisional se cambia por el componente real: 

    <int-checkbox … />

La página de cada componente muestra un chip Requires … con el estado de lo que necesita, y Reference → Status tiene la columna Requiere . Al marcar un componente como Done, /cambiar-estado avisa quién lo estaba esperando.

Cambiar el estado

Skill: /cambiar-estado

Cada versión de un componente tiene un estado que la página muestra como chip, junto a la versión. Así cualquiera sabe si el componente ya se puede usar. Avísale a la IA cuando empieces a maquetar y cuando termines.

Estado Chip Cuándo
pending Recién creado (componente o versión nueva): solo la estructura. Es el valor por defecto.
in-progress Lo estás maquetando.
done Terminado y listo para usar. Antes de marcarlo, la IA corre npm run check:component: si no cumple las bases, te sugiere estandarizarlo.

Qué te pregunta

  1. Componente : id o nombre visible.
  2. Estado : puedes decirlo con tus palabras ( terminado , listo , en progreso , pendiente ).
  3. Versión : por defecto la más reciente; solo pregunta si hablas de una anterior.

Cómo pedirlo

/cambiar-estado button in-progress
Ya terminé el accordion, márcalo como done
La versión 1 de tabs está lista
¿Qué componentes están pendientes?
El tooltip ahora lo ve Gabi

Qué cambia

src/components/button/version-1/base/button.ts

export class IntButton {
  /** Implementation status, shown on the documentation page: pending → in-progress → done. */
  static readonly status: 'pending' | 'in-progress' | 'done' = 'in-progress';
  /** Designer in charge of this version, shown on the documentation page and in Reference → Status. */
  static readonly designer = 'Yony León';
  …
}

Es la primera línea de la clase, así que también puedes cambiarla a mano: el editor te ofrece los tres valores. Es por versión: version-1 puede estar Done mientras version-2 sigue In progress . Una versión nueva empieza en Pending . Debajo va designer , el diseñador a cargo: el avance de cada uno se ve en Status .
